<p class="lead">THE STANDARDS REPOSITORY &mdash; At 10:24 AM Central on Tuesday, a full week before this edition went to press, the BSV standards repository merged its one and only change of the week. <a href="https://github.com/bsv-blockchain/BRCs/pull/373">Pull request #373</a> amends <a href="https://brc.dev/43">BRC-43</a>, "Security Levels, Protocol IDs, Key IDs and Counterparties," in 12 added lines and 7 removed ones. Its description ends with the most reassuring sentence in standards writing: "No behaviour change: the text documents what deployed implementations already do." TNT has spent seven days with this sentence and 125 satoshis' worth of follow-up questions.</p>

<h2>A Refresher, for the Three Readers Who Need One</h2>
<p>BRC-43 defines the invoice numbers that feed <a href="https://brc.dev/42">BRC-42</a> key derivation. An invoice number has three parts joined by hyphens: <code>&lt;securityLevel&gt;-&lt;protocolID&gt;-&lt;keyID&gt;</code>. Security level 0 needs no permission. Level 1 makes the user grant an application a protocol once, for every counterparty. Level 2 makes them grant it again for each new counterparty. The standard's own first example turns a protocol called <code>Hello World</code> and a key ID of <code>1</code> into <code>0-hello world-1</code>, which is the closest the BSV ecosystem has come to small talk.</p>
<p>None of that changed. What changed is the Rules section, which, in the words of the pull request, "has drifted from BRC-100 and from what the reference implementation enforces." Two documents in the same repository had been quietly disagreeing about the same numbers, and the software had been siding with the newer one the entire time.</p>

<h2>The Key ID Goes on a 233-Byte Diet</h2>
<p>The old text said a key ID must be "at least one byte and no more than 1033 bytes." The new text says no more than 800, "measured in its UTF-8 encoding." <a href="https://brc.dev/100">BRC-100</a> already said 800, and the pull request notes that the TypeScript SDK checks exactly that on every wallet call, as does the Go SDK. So the 233 bytes being removed were never actually available. TNT has asked where they went and been told they were never there, which is also what the paper's accountant says about its revenue.</p>
<p>The amendment also settles questions "implementers keep asking." Key IDs are free-form strings whose meaning each protocol defines, and they "need not be numeric." They "may contain any Unicode characters, including hyphens," which inside a hyphen-delimited format sounds like a dare. TNT notes that protocol IDs remain forbidden from containing hyphens, so the first two hyphens in the string still do the splitting, and the key ID may be as hyphenated as it likes. At four bytes per emoji, that is room for 200 emoji, should a protocol wish to express itself.</p>
<p>Most importantly, a key ID "is used exactly as given: it is not trimmed, case-folded or Unicode-normalized." The standard's example is <code>é</code> written as one code point, U+00E9, versus <code>e</code> followed by a combining accent, U+0301. They look identical and "derive different keys." TNT finds it bracing that a cryptographic standard will happily tell two indistinguishable strings that they are different people, and would like this energy applied to the replies section.</p>

<h2>Protocol Names Get a Raise</h2>
<p>Protocol IDs go the other way. The old limit was 280 characters, a number the industry may recognise from somewhere else. The new limit is 400, again matching BRC-100 and both SDKs. Protocols whose names begin with <code>specific linkage revelation </code>, from <a href="https://brc.dev/72">BRC-72</a>, may go up to 430, because, as BRC-100 puts it, that is "the only protocol that encapsulates another full protocol name within itself." A protocol name that contains another protocol name has, in other words, been given a 30-character allowance for the nesting, which is more than most of us get for bags.</p>
<p>Normalization is now described as a step, done "before use": remove leading and trailing whitespace, then convert to lower case. After that, a protocol ID must contain only lowercase <code>a</code> to <code>z</code>, digits and spaces, no double spaces, at least 5 characters, and must not end with <code>" protocol"</code>. All strings that normalize to the same value are the same protocol. The rule against naming your protocol "something protocol" survives intact. TNT considers it the single most enforced style guide in the BSV ecosystem, and has checked that its own name does not end in it.</p>
<p>Finally, the text now points readers to BRC-100's "Restrictions on Protocol and Basket Namespaces" for wallet-level rules, such as the reservation of the <code>p </code> prefix, which BRC-100 holds back for future "specially permissioned" protocols. The stated goal is that the rules "don't fork again." TNT is aware that this is a sensitive word in the BSV community and commends the author for using it in a pull request.</p>

<h2>Meanwhile, the Timeline Argued About Where Things Live</h2>
<p>While the standards repository tidied its naming rules, BSV X spent the week arguing about defaults. One builder said BSV Desktop, "the BRC100 reference implementation," <a href="https://x.com/ProjectBabbage/status/2119881535033938178">"keeps all transaction data local, and does not trace it"</a>, in reply to a post claiming the opposite. TNT takes no side on privacy, but observes that BRC-43's permission levels were written precisely so a user decides which application gets which keys, and that the spec spent its week on the character counts.</p>
<p>A second argument concerned the old ElectrumX servers. One side held that <a href="https://x.com/ProjectBabbage/status/2119544573798281666">"Syncing up ElectrumX is not cheap"</a> and that users relying on a free one <a href="https://x.com/ProjectBabbage/status/2119669221466710283">"are being subsidized."</a> The other built a transaction blaster and a 100,000-transaction test wallet, and reported that with a Rust server it <a href="https://x.com/cryptorebel_SV/status/2118898534959448233">"syncs in an hour."</a> TNT notes that the ecosystem built on paying for things has discovered that someone was paying for the free thing, and that "only an hour" is now a boast.</p>
<p>BSV Broadcaster v0.20.0, meanwhile, <a href="https://x.com/thebsvtimes/status/2117785444738040316">added a RECEIVED event</a>, so wallets learn the service has recorded a transaction "before network acceptance or block inclusion." Your payment can now be received, which is not the same as accepted, which is not the same as mined. Banks need three to five business days to say less.</p>

<h2>The Finance Desk</h2>
<p>The week's largest transaction was not a standard. Calvin Ayre <a href="https://x.com/CalvinAyre/status/2119792123373396326">posted</a> that he has "donated my BSV to BSV Association to help further their mission" and announced the Ayre Think Tank. The Association <a href="https://x.com/BSVAssociation/status/2119803748713406784">replied</a> with thanks for "Nearly a decade of backing," cited Teranode and the Chronicle upgrade, and promised "Full pace ahead." TNT will not speculate on the amount, as the posts do not state one. It notes only that on BSV the fee for moving it would be a fraction of a cent, and that skeptics immediately <a href="https://x.com/BHatooor13304/status/2119796248374923765">asked who is in charge of the Association</a>, because that is what skeptics are for.</p>
<p>Elsewhere, the Association reported <a href="https://x.com/BSVAssociation/status/2118402978226778132">"200+ builders. 30+ hours."</a> of agentic payments at a Munich hackathon, where AI agents paid each other in satoshis while some humans still ask what a wallet is. A wallet company <a href="https://x.com/ProjectBabbage/status/2119854300457512973">polled its followers</a> on whether they would buy cheese popcorn from it. TNT awaits the protocol ID, which must be at least five characters and must not end in " popcorn protocol."</p>

<h2>At Press Time</h2>
<p>At press time, one critic had written that BSV <a href="https://x.com/WuTao2023/status/2117750977512263795">"follows the whitepaper like a cover band follows the Beatles."</a> TNT accepts this gladly, since cover bands are paid per gig, which is a micropayment model. The same critic added that <a href="https://x.com/WuTao2023/status/2118059877792899113">"Only the AI image believes any of it."</a> TNT's header art has been consulted and confirms that it believes all of it, including the part where a 12-line amendment that changes nothing took a full page to explain.</p>
